# 实验二 实验报告：React 项目实战与 Zustand 状态管理

## 一、实验目的

- 掌握 React 项目从创建到部署的完整流程：脚手架建项目 → 写组件 → 管状态 → 持久化 → 上状态管理 → 构建部署。
- 用实验验证 React 核心机制：JSX 编译、state 挂 Hook 链表、组件重跑、key 稳定唯一、自定义 Hook 复用。
- 走完客户端状态管理的三步演进：useState → useLocalStorage → Zustand，并区分客户端状态与服务端状态。

## 二、实验环境

- 硬件：本机（Windows），可联网
- 软件：Node.js v22、pnpm 10、VS Code、Chrome + React DevTools
- 技术栈：React 19、Vite 8、Zustand 5、TanStack Query 5、json-server

## 三、项目简要设计（lab2-blog）

**组件树**：`App` → `Header`、`PostForm`、`CategoryFilter`、`PostList → PostItem`、`PostDetail`、`RemotePosts`

**数据结构**：`post = { id, title, category, summary, content, publishedAt }`，`posts = [post]`

**state 清单**：

| 组件 | 职责 | 要不要 state | state 放哪 | 接收的 props |
|---|---|---|---|---|
| App | 组装所有组件，持有全局状态与当前分类/查看文章 | 有 | Zustand store + useState | — |
| Header | 顶部标题与文章总数 | 无 | — | total |
| PostForm | 写文章表单（受控） | 有（草稿） | 组件内 | categories, onPublish |
| PostList | 列表渲染与空态 | 无 | — | posts, onOpen |
| PostItem | 文章卡片 | 无 | — | post, onOpen |
| PostDetail | 详情/编辑/删除 | 有（编辑态） | 组件内 | post, onBack, onEdit, onDelete |

**界面流程**：顶部博客名 → 写文章表单 → 分类过滤 → 文章卡片列表 → 点开详情 → 编辑/删除；底部为服务端文章区（TanStack Query 三态 + 乐观更新）。

**后端接口预留**：统一响应 `{ code, message, data }`，`src/api/client.js` 封装请求，`BASE_URL=""` 时走 `mock.js` 模拟后台；接入真实后台只改 BASE_URL，组件代码一行不用动。

## 四、实验内容

### 任务1：井字棋（lab2-tic）

- 拆了 3 个组件：`Square`（渲染一个格子，无 state）、`Board`（渲染九宫格）、`Game`（顶层持有历史状态）。
- state 放在 `Game`：history 数组存每步棋盘快照、currentMove 记当前步、xIsNext 由步数算出。棋盘数组更新用 `[...squares]` 复制后修改，因为 React 靠引用变化触发重渲染，直接改原数组界面不会更新。
- 时间旅行靠 `history[currentMove]` 回退：回到第 n 步就是把 currentMove 设成 n，之后落子会截断旧历史。

### 任务2：基础训练营 6 个练习

代码在 `training/`，每个训练一句话总结：

1. JSX 基础：JSX 里变量和表达式写在花括号里。
2. ES6 七语法：博客开发最常用的 ES6 语法是展开与 map。
3. useState 四连：数组操作必须用新数组替换（map/filter/展开），不能用 push。
4. 列表 + key：key 的作用是给 React 认节点。用 index 作 key，删除第一项后输入框内容串位；换成 id 后现象消失，因为 key 认错了节点。
5. useEffect 三形态：依赖数组告诉 React 什么时候重跑（不写=每次、[]=挂载一次、[count]=count 变了才跑）；闭包陷阱里 setTimeout 拿到的是本次渲染的旧 count，用函数式更新修复。
6. 自定义 Hook useWindowSize：自定义 Hook 复用的是逻辑，不是界面；必须以 use 开头。

### 任务3：Thinking in React 四步法

用官网「可搜索的产品表格」实例走完四步：拆组件（FilterableProductTable → SearchBar + ProductTable → ProductCategoryRow + ProductRow）→ 写静态版 → 找 state（searchText、inStockOnly；过滤列表从 state 算出，不设冗余 state）→ 确定位置（放在共同最近父组件 FilterableProductTable）。

### 任务4：手写博客 13 步

按官网训练线完成：建项目 → 七个组件骨架 → JSX 界面 → props 传参 → 条件渲染（空态/徽章/摘要兜底）→ map 渲染列表（key={post.id}）→ 响应事件（onSubmit 拦截刷新）→ useState 五小步 → 数组更新用新数组 → 剔除冗余 state（总数从 posts 算出）→ 状态提升（分类/当前文章提升到 App）→ useLocalStorage 持久化 → 构建部署。

### 任务5：Zustand 与 TanStack Query

- **Zustand**：`usePostStore` 用 `create + persist`，posts 全局共享，`partialize` 只持久化 posts。F5 刷新数据不丢（persist 生效），各组件不再层层传 props，直接 `usePostStore()` 读 store。
- **TanStack Query + json-server**：`RemotePosts` 用 `useQuery` 三态渲染（pending/error/success），`--delay 500` 让 pending 肉眼可见；新增文章走 `useMutation` 乐观更新四件套（onMutate 快照 → 乐观插入秒出 → onError 回滚 → onSettled 重拉）。

## 六、必答问题

**（1）为什么把 Hook 写在 if 里是必然出错而不是偶尔出错？**

Hook 按调用顺序在组件对应的链表上排队领号（hookIndex 递增）。如果某次渲染 if 条件不成立导致某个 Hook 没被调用，下次渲染时它的序号会被后面的 Hook 顶替，React 拿到的就是错位的 state，行为完全不可预测。所以条件分支会改变 Hook 调用次数，是必然出错，不是概率问题。

**（2）useState / useLocalStorage / Zustand 的选择思路？**

- useState：状态只在单个组件内用。
- useLocalStorage：需要刷新不丢，且共享范围仍小（如单个组件的持久化设置）。
- Zustand：跨多个组件、甚至跨大半个应用共享，还要持久化。

反例：把「当前查看的文章 id」放进 Zustand，其实它只被 App 和 PostDetail 用到，提升到 App 用 useState 就够。为了全局而全局，状态散落在外，调试和测试都变麻烦，这就是「该用 useState 却硬用 Zustand」的反面教材。

## 八、实验体会

这次实验把 React 从建项目到部署完整走了一遍。最有体会的是两点：一是状态放哪一层直接决定组件的耦合度，Zustand 把「层层传 props」变成「需要的地方直接读 store」，代码清爽很多；二是「服务端状态 ≠ 客户端状态」，TanStack Query 的三态和缓存跟 Zustand 完全是两套思维，之前容易混在一起。井字棋的时间旅行让我真正理解了「数组不可变更新」为什么是 React 的底线。
